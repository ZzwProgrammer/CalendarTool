# 语音日历工具 - 需求文档

## 1. 项目背景

用户在日常日历管理中经常需要快速记录或查询事件，但传统的图形界面操作步骤繁琐。本项目旨在开发一个以**语音交互为核心**的日历管理工具，让用户通过自然语言即可完成事件的添加、删除和查看，提升效率和便捷性。

## 2. 项目目标

- 实现一个**纯前端、零服务器**的语音日历工具，可在主流浏览器中运行。
- 支持**中文语音输入**，准确识别用户意图（添加/删除/查看）及事件信息（时间、内容）。
- 提供简单的图形化日历视图作为辅助反馈，但核心交互为语音。
- 所有数据保存在用户浏览器本地（IndexedDB / LocalStorage），不上传任何隐私信息。

## 3. 用户角色

- 普通用户：希望通过语音快速管理个人日程。

## 4. 功能需求

### 4.1 语音添加事件

- **输入**：用户说出类似“添加一个明天下午三点的团队会议”的语句。
- **处理**：
    - 语音识别 → 文本
    - 意图识别 → “添加”
    - 时间抽取 → 2026-05-31 15:00:00
    - 事件标题抽取 → “团队会议”
- **输出**：
    - 系统语音反馈：“已添加团队会议，时间明天下午三点。”
    - 日历视图即时更新显示新事件。
- **异常处理**：
    - 若缺少时间 → 追问：“请问事件安排在什么时间？”
    - 若缺少标题 → 追问：“事件名称是什么？”

### 4.2 语音删除事件

- **输入**：“删除明天的会议”
- **处理**：
    - 定位到明天（2026-05-31）所有标题包含“会议”的事件。
    - 若匹配唯一 → 直接删除。
    - 若匹配多个 → 语音列出选项并让用户选择（例如“找到两个会议：团队会议和客户会议，请问删除哪一个？”）。
    - 若无匹配 → 语音反馈：“明天没有找到名为‘会议’的事件。”
- **输出**：删除后语音确认，日历视图刷新。

### 4.3 语音查看事件

- **输入**：“显示这周五有什么安排” / “明天有什么会”
- **处理**：
    - 解析时间范围（某一天或某几天）。
    - 查询本地存储中对应日期的事件列表。
- **输出**：
    - 语音合成朗读事件列表（如“周五共有2个事件：上午十点代码评审，下午三点团队会议”）。
    - 同时在日历视图中高亮显示对应日期的事件。

### 4.4 图形界面辅助

- 提供按月/周/日展示的日历视图（使用轻量级库如 FullCalendar 或原生表格）。
- 用户可手动点击编辑或删除事件，保证语音操作有后备方案。
- 每次语音操作的结果以**卡片形式**展示解析后的结构化信息，允许用户确认或手动修正。

### 4.5 唤醒词模式（可选，时间允许则实现）

- 支持连续监听，当用户说出"嘿日历"后自动进入命令模式，无需点击按钮。

### 4.6 语音纠错与模糊澄清机制（核心）

语音识别在真实环境中不可避免会产生错别字（如"会议"被识别为"回忆"、"下午三点"被识别为"下五删点"），这将导致下游意图理解和时间提取全部失败。因此需要引入**三级分层防御架构**，从轻到重逐级兜底。

#### 4.6.1 第1层：本地模糊匹配与纠错（必须实现，离线可用）

- **音近词纠错表**：维护中文语音识别常见同音字/近音字错误映射（如 `回忆→会议`、`下五→下午`），在原始文本上先执行纠错替换。
- **编辑距离模糊匹配**：对意图关键词（添加/删除/查看）做 Levenshtein 编辑距离匹配，容忍 1~2 个字符的识别偏差。
- **chrono-node 前置清洗**：对时间表达做预处理归一化（如 `下五三点`→`下午三点`、`明个`→`明天`），提高时间解析成功率。
- **自适应纠错知识库**：用户每次手动修正确认卡片中的内容时，系统自动记录 `原始识别词→用户修正词` 的映射关系，持续学习用户特定口音的识别误差模式。

#### 4.6.2 第2层：LLM 语义兜底（可选增强，网络依赖）

当本地纠错层置信度低于阈值时，调用大语言模型做语义级纠错和理解。

- **角色设定（System Prompt）**：将 LLM 设定为"语音日历纠错引擎"，明确告知常见的识别错误模式，要求输出结构化 JSON。
- **功能**：即便原始文本存在多处同音字错误，LLM 仍能从语义层面推断真实意图，并输出纠错后的完整文本、意图、时间、事件标题及置信度。
- **输出格式**：统一的 JSON 结构，包含 `correctedText`、`intent`、`datetime`、`title`、`confidence`、`correctionNote` 字段。
- **调用策略**：仅在本地层置信度 < 0.5 时触发，用量极低，成本和隐私影响可控。若 LLM 输出置信度仍 < 0.9，则进入第3层。
- **离线备选**：可考虑使用 WebLLM（浏览器端运行小模型）实现离线 LLM 纠错。

#### 4.6.3 第3层：UI 确认与澄清（永远保留的最后防线）

无论前两层结果如何，系统都根据**置信度**决定后续行为，绝不静默执行错误操作：

| 置信度 | 策略 |
|--------|------|
| > 0.9 | 直接执行，Toast 提示 + 提供"撤销"入口 |
| 0.6 ~ 0.9 | 展示确认卡片，默认高亮解析结果 |
| < 0.6 | 展示确认卡片 + 高亮标注疑似错误字段，允许用户手动编辑每个字段 |

确认卡片包含：原始识别文本、自动纠正说明、可编辑的事件标题/时间/操作类型、确认/手动修改/取消三个按钮。

#### 4.6.4 置信度机制

每个处理环节都需输出置信度（0~1），下游据此决策：

```
原始文本 → [音近词纠错] → confidence_A → [编辑距离匹配] → confidence_B
    → [chrono-node解析] → confidence_C → 综合置信度 = f(A,B,C)
    → 若综合置信度 < 0.5 → 触发 LLM 兜底
    → 最终 < 0.9 → 触发 UI 确认卡片
```

## 5. 非功能需求

| 需求项 | 指标 |
|--------|------|
| **语音识别准确率** | 安静环境下中文普通话识别准确率 ≥ 90% |
| **意图理解准确率** | 针对常用表达（添加、删除、查看）准确率 ≥ 95% |
| **响应速度** | 从用户说完到语音反馈 < 1.5 秒 |
| **离线可用性** | 时间解析、事件存储、日历显示完全离线；语音识别依赖浏览器服务（部分浏览器需网络） |
| **数据隐私** | 不向任何服务器发送语音或文本数据，所有事件仅存在用户浏览器本地 |
| **浏览器兼容** | Chrome / Edge / Safari（最新两个版本） |
| **代码可维护性** | 模块化 JavaScript，清晰的目录结构，充分的注释 |

## 6. 技术选型

基于讨论结论，采用**轻量级纯前端方案**，避免使用后端和云 API。

| 模块 | 技术 | 理由 |
|------|------|------|
| 语音识别 | Web Speech API (`SpeechRecognition`) | 浏览器原生支持，免费，实时，零配置 |
| 语音合成 | Web Speech API (`SpeechSynthesis`) | 同上，用于朗读反馈 |
| 意图理解 | 规则匹配 + `chrono-node` | 速度快，离线可用，覆盖日历场景常见表达 |
| 语音纠错（第1层） | 音近词映射 + Levenshtein 编辑距离 + 自适应纠错知识库 | 零成本、离线、针对中文同音字识别错误做模糊匹配 |
| LLM 兜底（第2层） | LLM API（如 DeepSeek / 通义千问）或 WebLLM 浏览器端推理 | 处理严重识别错误和复杂语义，按需调用频率极低；WebLLM 可离线运行小模型 |
| 时间解析 | `chrono-node`（支持中文） | 成熟稳定，支持模糊时间 |
| 数据存储 | IndexedDB（或 LocalStorage） | 浏览器内置，无需后端数据库 |
| 日历视图 | FullCalendar（轻量库）或原生 JS 表格 | 快速构建可视化日历，提升用户体验 |
| 前端框架 | 原生 HTML/CSS/JS | 无依赖，提高开发和运行效率 |
| 部署 | GitHub Pages / Vercel | 免费 HTTPS，与 GitHub 仓库无缝集成 |

## 7. 交互流程示例

### 添加事件完整流程（含纠错层）

1. 用户点击"开始语音"按钮（或通过唤醒词激活）。
2. 用户说话："帮我添加一个下午三点与团队的设计评审"
3. 浏览器语音识别返回文本（假设含错别字）："帮我田家一个下五三点与团队的设计平身"
4. **第1层纠错**：音近词映射 `田家→添加`、`下五→下午`、`平身→评审`，编辑距离匹配修正后→"帮我添加一个下午三点与团队的设计评审"。
5. 意图识别器匹配关键词"添加" → intent=add。
6. `chrono-node` 解析出时间"下午三点" → 当天 15:00。
7. 移除时间和意图词后剩余"与团队的设计评审" → title。
8. 综合置信度 0.95 → 直接展示确认卡片（标题、时间、操作按钮）。
9. 用户语音说"确认"或直接点击确认。
10. 事件存入 IndexedDB，日历视图刷新，语音朗读："已添加与团队的设计评审，时间今天下午三点。"

### LLM 兜底流程（严重识别错误场景）

1. 用户说话："帮我把明天下午的设计评审改到下周五上午十点"
2. 浏览器语音识别返回文本（严重失真）："帮我把明天下午的射击平身改道下周无上五原点"
3. 第1层本地纠错仅能修正部分词（`射击→设计`、`平身→评审`），但"改道"、`无`、`原点`无法匹配，综合置信度仅 0.35。
4. **第2层 LLM 兜底**：将原始文本和当前日期发送给 LLM，System Prompt 设定为"语音日历纠错引擎"角色。
5. LLM 返回：`{"correctedText":"帮我把明天下午的设计评审改到下周五上午十点","intent":"reschedule","datetime":"2026-06-05T10:00:00","originalDatetime":"2026-05-31T14:00:00","title":"设计评审","confidence":0.88}`
6. LLM 置信度 0.88 < 0.9 → **第3层 UI 确认卡片**展示纠错结果，高亮标注可疑字段。
7. 用户确认后执行。

### 删除事件异常流程

1. 用户："删除明天的会议"
2. 系统查找明天所有标题含"会议"的事件，假设找到 0 个。
3. 语音反馈："明天没有名为'会议'的事件，请确认事件名称或日期。"
4. 用户重新尝试。

## 附录：关键设计决策说明

| 问题 | 决策 | 原因 |
|------|------|------|
| 为什么不用 LLM 做主意图理解？ | 仍采用轻量级规则 + chrono-node 作为主路径 | 保证核心流程离线可用、零延迟、零成本；规则引擎覆盖增删查场景足够 |
| 为什么引入 LLM 做纠错兜底？ | LLM 作为第2层语义兜底，仅在本地纠错置信度 < 0.5 时按需调用 | LLM 对同音字错误有天然鲁棒性，能有效恢复严重失真的识别文本；按需调用频率极低，成本可控；角色设定 + few-shot 提示词可精准适配日历场景 |
| 为什么需要三级分层防御？ | 本地模糊层 → LLM兜底层 → UI确认层 | 单一纠错手段不可靠；分层架构让大部分场景在离线本地层解决，仅极端情况才走LLM或用户确认，在鲁棒性、成本、体验之间取得平衡 |
| 为什么不用后端？ | 纯前端实现 | 简化部署，隐私安全，符合竞赛全周期快速迭代的需求 |
| 为什么不用 Google Calendar API？ | 使用本地存储 | 避免 OAuth 复杂授权，保证演示稳定性 |
| 如何保证删除事件准确性？ | 模糊匹配 + 多选确认机制 | 在简单性和用户体验之间取得平衡 |
